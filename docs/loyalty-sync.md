# Loyalty sync (VM Hub loyalty & customer reports → Supabase)

Seven customer-level VM Hub charts, synced by `src/loyalty.js`
(`npm run sync:loyalty`). They are **not** in `REPORTS` and **not** run by
`npm run sync`: `index.js` skips `vm_refresh_all_snapshots()` if any report
fails, and a heavy customer-level chart must never block that refresh. The
weekly workflow runs the loyalty step **after** the core sync and its refresh.

Everything here was measured against the live hub on 2026-10-15
(`src/inspect_loyalty.js`, read-only), not assumed.

---

## 1. Report → table map

| Chart (exact dropdown text) | Table | Kind | Stores | Key kept | Personal data dropped |
|---|---|---|---|---|---|
| `Loyalty earnt and redeemed` | `vm_loyalty_earnt_redeemed` | **snapshot** | per store | `uuid` | `email` |
| `Loyalty per channel` | `vm_loyalty_per_channel` | weekly | per store | — (aggregate) | — |
| `Loyalty per customer (with filters)` | `vm_loyalty_per_customer` | weekly | per store | `user_uuid` | — |
| `Discounts Info (with promo code & customer info)` | `vm_discounts_info_customer` | weekly | per store | `order_uuid` | `customer_name`, `user_email`, `marketing_opt_in` |
| `Lifetime loyalty per customer` | `vm_loyalty_lifetime_per_customer` | **snapshot** | estate-wide → `store = 'All stores'` | `user_uuid` | — |
| `Users` | `vm_loyalty_users` | weekly (sign-ups) | per store | `user_uuid` | `email`, `name`, `user_phone_number`, `birth_date`, `marketing_opt_in`, `acteol_ctc_id` |
| `Sales Generated by Discount Type` | `vm_sales_by_discount_type` | weekly | per store | — (aggregate) | — |

Notes per chart:

- **Loyalty earnt and redeemed** — one row per loyalty member *attributed to the
  selected store* (uuid unique per store; Hitchin's and Stevenage's member sets
  don't overlap). Per-member running totals (`balance_accrued`,
  `balance_redeemed`, `current_balance`) plus `last_activity_date`. It is **not**
  an event ledger, and the date range is ignored. 14,609 rows across both stores
  versus 2,862 in Lifetime: 8,427 of them (Hitchin 4,840, Stevenage 3,587) have
  `last_activity_date` exactly `2026-04-14T01:00:03Z` — a bulk import/launch
  stamp, i.e. members carried over with a balance but no activity in Vita Mojo
  since. Weekly loyalty activity before mid-April is therefore zero in the
  weekly charts. Every Lifetime member appears in exactly one store's list here; their
  balances only match Lifetime's `points_balance` for ~1 in 3, so the two charts
  define "balance" differently — don't mix them.
- **Loyalty per channel** — values are each channel's **share** (they sum to 1
  per store-week), not points. Don't sum across stores.
- **Discounts Info** — one row per discounted order. It has **no customer id**;
  `order_uuid` joins to `vm_detailed_sales_info.order_uuid` → `customer_id`.
  Its own `store` column lands as `store_2` (see load.js).
- **Lifetime loyalty per customer** — identical output whatever the Stores filter
  says, so it is pulled once and loaded as `'All stores'` (never under both
  store names — that would double count).
- **Users** — customers only (`user_role = customer`), filtered by
  `registered_at`, so it is a weekly **sign-up list** and can be backfilled.
  `store` lands as `store_2`.
- **Sales Generated by Discount Type** — heavy Metabase query: ~130 s cold for
  one store-week, and a 504 on the first fetch is normal. It gets a 300 s CSV
  timeout and gateway retries, and runs **last**.
- **Loyalty - Current Balance** — *not synced*: its CSV has headers but zero
  rows for every store selection.

## 2. Weekly vs snapshot

- **weekly** — output changes with the date range. One load per
  `(store, Mon–Sun week)`, exactly like the core sync. Backfillable.
- **snapshot** — output is point-in-time state and ignores the date range.
  Pulled **once per run** and stamped with the week being synced
  (`week_start` = Monday of the last complete week). Each weekly run adds one
  more `week_start`, building a history (e.g. member balances week by week).
  Snapshots are **never backfilled**: past weeks would get today's numbers, so
  `LOYALTY_FROM` mode skips them.

## 3. Personal data rule (mandatory)

`load.js` turns every CSV header into a `TEXT` column, so personal data is
removed **before** `loadStore()` — and before anything is written to disk:

- Header rules: `LOYALTY_PII_DEFAULT` in `src/config.js` (names, email,
  phone/mobile, address/street/postcode/zip, birthday/DOB, marketing/consent/
  opt-in, card/payment tokens) plus each report's `dropColumns`.
- The Vita Mojo customer/user uuid (or `order_uuid`) is **kept** — pseudonymous,
  and it is what joins to `vm_detailed_sales_info`.
- Columns are removed from `columns` **and** every row; the dropped headers are
  logged per unit and in the run summary.
- The raw CSV is **never written** (`captureViaCsv(..., { persist: false })`);
  `downloads/` only gets the stripped copy. No `DEBUG_SHOTS` screenshots are
  taken in this step (the workflow uploads `debug/` on failure).
- **Fail closed** (the unit is not loaded): any new or missing header versus
  `LOYALTY_REPORTS[].columns`, a missing id column, an email-like value left
  after stripping, or a CSV `store` value that isn't the filtered store.
  A new header on a customer chart may be personal data — review it, then add it
  to `columns` (and `dropColumns` if needed).
- `npm run verify:loyalty` checks `information_schema.columns` and exits
  non-zero if any loyalty table has a personal-data column.

## 4. Running it

```bash
npm run sync:loyalty                      # last complete week + snapshots
npm run sync:loyalty -- --dry-run         # extract + validate + counts, no writes
```

Backfill (weekly reports only; run **locally**, not in Actions — the full range
is hours, mostly `Sales Generated by Discount Type`):

```bash
LOYALTY_FROM=2026-03-02 npm run sync:loyalty
```

| Env / flag | Effect |
|---|---|
| `LOYALTY_FROM=YYYY-MM-DD` | Backfill one window per Mon–Sun week from that Monday to the last complete week. Must be a Monday. |
| `LOYALTY_TO=YYYY-MM-DD` | Optional last Monday of the backfill (for test slices). |
| `LOYALTY_ONLY=table,table` | Only these tables (e.g. run the slow discount chart separately). |
| `SKIP_LOYALTY=1` | Do nothing, exit 0 — the kill switch. |
| `--dry-run` | No Supabase writes, no files, no progress entries. |
| `--no-resume` | In backfill mode, redo units already logged as done. |

`START_DATE` / `END_DATE` are **ignored** by this step (`getWeeks()` with both set
returns ONE window; the loyalty step has its own `getLoyaltyWeeks()`).

**Resumable**: every `(report, store, week)` is its own extract +
`loadStore()` transaction, logged to `downloads/loyalty_progress.jsonl`. A
backfill re-run skips units logged `ok`. `loadStore()` is delete-then-insert per
`(store, week_start)` and only for the weeks in the run, so redoing a unit is
always safe.

PowerShell equivalents: `$env:LOYALTY_FROM='2026-03-02'; npm run sync:loyalty`
(clear with `Remove-Item Env:LOYALTY_FROM`).

## 5. Weekly workflow

`.github/workflows/sync.yml` step **Run loyalty sync (previous complete week)**:
after `Run sync`, `if: !cancelled() && steps.auth.outcome == 'success'` (so it
still runs when a core report failed), `timeout-minutes: 25`. Job timeout is 90.
A loyalty failure fails the job, but only after the core data and the snapshot
refresh have committed. The `skip_loyalty` dispatch input sets `SKIP_LOYALTY`.

Timing (2026-10-15, 1 week × 2 stores + snapshots): **9.7 min** total; the
Stevenage `Sales Generated by Discount Type` unit alone took 297 s after a 504.

## 6. VM Hub quirk handled in this step only

Typing a start date that is **after** the current end date leaves the start
calendar open over the end input, and the end click times out. Backfills walk
forward, so `src/loyalty.js` sets the end date first whenever the window moves
forward. Core `setDate()` is unchanged — it can hit the same trap when
`WEEKS_BACK > 1` (open follow-up).
